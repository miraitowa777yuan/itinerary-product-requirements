# 产品需求文档（PRD）

## 1. 文档信息

- 产品代号：行程计划器（暂定）
- 文档版本：v0.1
- 状态：需求基线
- 目标发布载体：微信小程序
- 未来载体：响应式 Web / 桌面浏览器

## 2. 背景与机会

一次旅行的信息通常散落在购票应用、酒店订单、短信、聊天记录、截图、邮件和备忘录中。备忘录能记录文字，却不理解时间衔接、地点迁移、入住关系、订单凭证、同行协作和临近提醒。

本产品的机会不是提供另一个文本编辑器，而是建立一个“旅程模型”：系统知道哪些项目属于同一次旅行、前后如何衔接、当前进行到哪里、下一步需要用户做什么。

## 3. 产品愿景

让用户在旅行前获得秩序、旅行中获得确定感、旅行后保留一份可回看的旅程档案。

## 4. 目标与成功标准

### 4.1 用户目标

- 在一个地方管理交通、住宿、活动与重要资料。
- 10 秒内确认下一项安排的时间、地点和必要凭证。
- 在手机与电脑之间无缝继续编辑。
- 与同行者共享必要信息，而非反复转发截图。
- 行程变化后能快速修正，避免旧信息继续误导。

### 4.2 产品目标

- 首次创建一段含 3 个项目的旅行可在 5 分钟内完成。
- 高频项目类型的录入步骤清晰且可预测。
- 用户返回产品后，可直接定位“当前 / 下一项”行程。
- 离线或弱网时仍可查看最近同步的核心行程信息。
- 所有关键编辑均有明确保存状态，并能降低误删风险。

### 4.3 建议观测指标

- 创建旅行完成率
- 首次旅行中添加 3 个及以上项目的比例
- 单项目创建用时与放弃率
- 旅行期间日活跃天数
- “下一项行程”查看次数
- 分享邀请成功率与同行者查看率
- 识别导入后的字段修正率（后续版本）

指标用于判断体验，不用于诱导用户增加无意义使用时长。

## 5. 目标用户

### 5.1 核心用户：主动规划者

经常负责自己或家人朋友的旅行安排，会同时处理多张票、多个酒店和若干活动。重视确定性与信息完整，希望整理后能让同行者放心。

### 5.2 次级用户：同行查看者

不负责主要规划，但需要随时知道集合时间、下一站、酒店地址和票务凭证。主要查看，偶尔补充或确认信息。

### 5.3 延伸用户：差旅人士

短时间内频繁出行，更关注效率、交通衔接、地址、报销凭据与多端编辑。

## 6. 核心使用场景

1. 用户确定出行后创建一段旅行，录入往返交通和酒店。
2. 用户在电脑上集中整理每天的活动，在手机上随时补充。
3. 出发当天，用户打开产品立即看到下一班车 / 航班、出发地、时间和凭证入口。
4. 到达目的地后，产品自然切换关注点到取行李、交通接驳或酒店入住。
5. 计划变化时，用户修改时间或取消项目，后续安排中的冲突得到提示。
6. 用户邀请同行者，共享整段旅行或选定项目。
7. 用户在弱网环境下查看已经保存的地址、车次、订单号和备注。
8. 旅行结束后，用户回看足迹，并可复制行程作为新旅行模板。

## 7. 产品范围

### 7.1 P0：最小可用版本

#### 账户与同步

- 微信授权登录。
- 账户下的旅行和项目云端保存。
- 多设备打开后数据一致。
- 展示保存中、已保存、同步失败等状态。

#### 旅行管理

- 创建、编辑、归档和删除旅行。
- 字段：旅行名称、目的地、开始 / 结束日期、时区、封面素材（可选）、备注。
- 状态：未开始、进行中、已结束、已归档。
- 支持跨城市、多日、跨时区旅行。

#### 行程项目

- 支持类型：航班、火车 / 高铁、酒店、活动、餐饮、当地交通、自定义事项。
- 公共字段：标题、开始 / 结束时间、时区、地点、地址、备注、附件、状态。
- 类型专属字段见数据模型文档。
- 新建、编辑、复制、取消、删除和恢复。
- 支持无明确时间的“当天事项”。
- 支持跨日项目，例如夜间航班和连续住宿。
- 对尚未开票或尚未购买的火车 / 高铁行程，支持标记为“待抢票”；该状态必须在旅程浏览和项目详情中清晰可见。
- “待抢票”项目可记录预计开售时间、期望席别与抢票提醒。P0 由用户手动设置和更新状态，不承诺自动购票。

#### 旅程呈现

- 按旅行和日期组织所有项目。
- 明确当前正在发生、下一项和已完成项目。
- 用户可快速查看时间、地点、状态和关键凭证。
- 支持展开项目详情，并直达地图、电话、订单或附件等外部动作。
- 时间冲突、地点衔接过紧等情况应有非阻断式提示。

#### 搜索与查找

- 在当前旅行中按标题、地点、车次 / 航班号、酒店名搜索。
- 可按日期和项目类型筛选。

#### 基础分享

- 生成旅行邀请。
- 角色：所有者、可编辑同行者、只读同行者。
- 所有者可以撤销成员权限。
- 分享页面默认隐藏敏感字段，除非所有者明确授权。

#### 提醒

- 用户主动订阅后，按项目设置提醒。
- 支持固定提前量和自定义时间。
- 提醒内容只展示完成行动所需的最少信息。
- “待抢票”火车 / 高铁项目可围绕预计开售时间设置专门提醒；未填写开售时间时，应提示用户补充，而不是虚构时间。

#### 弱网保障

- 缓存近期旅行与关键详情。
- 无网时明确标记离线状态与最后同步时间。
- 离线编辑进入待同步队列，冲突时要求用户确认，不静默覆盖。

### 7.2 P1：增强版本

- 粘贴订单文本并解析为结构化项目。
- 上传酒店、航班、高铁 / 火车和城际巴士购票截图进行 OCR；识别酒店城市、名称、房型、日期，以及交通班次、起终点、日期时间和舱位 / 席别，用户确认后导入。
- 使用腾讯地图计算时间线上相邻机场与酒店之间的驾车时长，并缓存结果。
- 高铁 / 火车项目允许用户手动切换“已出票”和“待抢票”。
- 项目间衔接提醒，如机场到酒店。
- 日历订阅 / 导出。
- 旅行模板与整段复制。
- 费用记录与多人分摊的基础能力。
- Web 端集中整理。
- 变更历史与简单撤销。

### 7.3 P2：智能版本

- 经用户明确授权后，从邮件或第三方来源导入订单。
- 航班 / 列车动态服务接入。
- 基于地点与时间的冲突检测。
- 行程优化建议，但不自动更改用户计划。
- 旅行结束后的足迹回顾与可控分享。

### 7.4 明确不做

- 不直接售卖机票、火车票或酒店。
- 不做以广告和种草为核心的旅游社区。
- 不未经确认自动修改用户行程。
- 不默认公开旅行位置、订单或同行人信息。
- 不以复杂项目管理工具的方式要求用户维护大量状态。

## 8. 关键业务规则

### 8.1 时间

- 每个时间字段同时保存本地时间、IANA 时区和标准时间。
- 跨时区交通分别记录出发地与到达地时区。
- 全天事项不伪造具体时间。
- 行程排序首先依据确定的开始时间，其次依据用户手动顺序。

### 8.2 状态

- 项目状态至少包含：计划中、已确认、进行中、已完成、已取消。
- 火车 / 高铁项目增加预订状态“待抢票”，表示行程意向已确定，但车票尚未开售或尚未购买。它不是交通运行状态，也不表示系统正在自动代购。
- “待抢票”的推荐流转为：待抢票 → 已出票 / 已确认；若用户放弃该车次，则转为已取消或删除。开售后仍未购买时，可以继续保持“待抢票”，但应突出其待办属性。
- 系统可根据时间推断展示状态，但用户的明确状态优先。
- 已取消项目默认弱化而非立即删除，以保留变化上下文。

### 8.3 冲突

- 时间重叠、跨城移动时间不足、酒店入住和离店异常等属于提示，不强制阻止保存。
- 提示必须说明依据，并允许用户忽略。

### 8.4 权限

- 所有者拥有旅行及成员管理权。
- 编辑者可编辑普通项目，但不可转移所有权或扩大他人权限。
- 查看者不可修改内容。
- 敏感字段拥有独立可见性设置。

### 8.5 删除与恢复

- 删除旅行或项目需二次确认。
- P0 建议提供 30 天回收站；若首发不能实现，至少提供短时撤销。

## 9. 非功能需求

### 9.1 性能

- 已缓存旅行的核心内容应快速可见，避免每次打开都等待完整网络请求。
- 长行程采用分段加载，但当前日期和下一项优先。
- 图片与附件生成缩略图，原件按需加载。

### 9.2 可靠性

- 创建和编辑采用本地乐观更新，并清楚反馈同步结果。
- 服务端保留更新时间与版本号，防止多端静默覆盖。
- 关键写入应具备幂等性。

### 9.3 隐私与安全

- 数据传输全程加密，敏感字段服务端加密或采用等效保护。
- 订单号、证件信息、二维码等默认不出现在锁屏通知和分享预览中。
- 附件使用有时效的受控访问地址。
- 提供账户数据导出与删除能力。
- 记录成员权限变更和敏感内容访问所需的最小审计信息。

### 9.4 可访问性

- 关键状态不可只依赖颜色表达。
- 支持系统字体缩放和足够大的触控区域。
- 动效可随系统“减少动态效果”设置降级。
- 屏幕阅读器可读出项目类型、时间、状态与操作。

### 9.5 国际化准备

- P0 可只提供简体中文，但时间、地址、电话号码、货币与时区的数据结构不可绑定单一地区格式。

## 10. 跨端策略

### 微信小程序

- 旅行途中主入口。
- 优先解决快速查看、即时操作、提醒和轻量编辑。
- 适配手机，并保证在电脑版微信中基本可用。

### Web

- P1 建设，面向电脑浏览器。
- 优先解决批量整理、跨日调整、附件管理和高信息密度编辑。
- 与小程序共享账户、数据模型、权限和同步协议，不另建孤立数据。

## 11. 风险与待验证假设

- 用户是否愿意手动维护行程，取决于录入速度和旅行中获得的回报。
- 电脑版微信内的小程序不足以替代专门 Web 端的高效整理体验。
- 自动识别的价值很高，但错误导入可能降低信任，因此必须“识别—确认—保存”。
- 提醒能力受平台订阅机制约束，需要在实际小程序实现前验证最新规则。
- 航班与列车动态依赖第三方数据授权、成本与覆盖率，不应成为 P0 前置条件。

## 12. 开放问题

- 产品最终名称与品牌气质。
- 首发更偏个人旅行还是多人同行。
- 是否允许记录证件信息；若允许，需要更严格的安全方案。
- Web 端登录方式及与微信账户的绑定方式。
- 地图、航班动态、OCR 服务的供应商与成本。
- 小程序主体类型、服务类目、隐私协议与上线审核要求。
