# 信息架构与核心流程

本文描述“用户需要理解和完成什么”，不规定页面应长什么样。

## 1. 核心心智模型

```text
账户
└── 旅行 Trip
    ├── 日期 / 阶段
    │   └── 行程项目 Item
    ├── 资料与附件
    ├── 同行成员
    ├── 提醒
    └── 变更与同步状态
```

用户首先进入“一段旅行”，再理解其中正在推进的安排。日期是重要组织方式，但不是唯一方式；跨日交通、连续住宿和无具体时间事项不能被强行切碎。

## 2. 顶层能力

### 旅行入口

- 即将开始 / 进行中的旅行
- 过去旅行
- 新建旅行
- 搜索与账户设置

### 旅行内部

- 当前与下一项
- 全程安排
- 按日浏览
- 资料与凭证
- 同行成员
- 旅行设置

具体导航形式由设计阶段决定，不要求采用传统底部标签栏。

## 3. 核心流程

### 3.1 首次创建旅行

1. 用户输入名称、目的地和日期。
2. 系统生成空旅行，并提供最符合当前上下文的添加入口。
3. 用户添加第一项交通或住宿。
4. 系统根据首个项目补全或建议旅行日期、城市和时区。
5. 用户继续添加，或稍后返回。

要求：创建旅行不应以填写完整资料为前提。

### 3.2 添加行程项目

1. 用户选择项目类型或使用自然语言 / 粘贴内容入口（后续）。
2. 先填写决定排序和识别的核心字段。
3. 其他字段按类型逐步显现。
4. 保存前展示必要的时间、时区或冲突提示。
5. 保存后回到旅行上下文，并突出新项目的位置。

要求：不同类型可以有不同录入方式，不必被统一大表单限制。

### 3.3 旅行当天查看下一步

1. 系统根据当前时间、项目状态和用户位置授权情况确定关注点。
2. 用户立即得到下一项的时间、地点、凭证和建议出发时间（若有）。
3. 用户可以完成常见动作：导航、致电、查看票据、标记完成或报告变更。
4. 当前项目结束后，关注点平滑转移到下一项。

要求：不要让用户先选择日期再寻找当前事项。

### 3.4 修改与取消

1. 用户进入项目并修改字段或设为取消。
2. 系统指出对相邻项目的潜在影响。
3. 用户确认保存。
4. 同行者收到适度的变化提示；敏感信息不进入通知。

### 3.5 分享同行

1. 所有者选择分享范围和权限。
2. 系统生成有时效或可撤销的邀请。
3. 接收者确认加入。
4. 所有者可随时更改角色、字段可见性或移除成员。

### 3.6 弱网与多端冲突

1. 用户离线编辑，系统保留本地变更并标记待同步。
2. 恢复网络后自动尝试同步。
3. 若服务端同一项目已变化，显示字段级差异。
4. 用户选择保留某一版本或合并，不做静默覆盖。

## 4. 信息优先级

### 一级：当下行动信息

- 是否需要立即行动
- 下一项是什么
- 何时开始 / 应何时出发
- 去哪里
- 最关键凭证或入口

### 二级：完成行动所需信息

- 航站楼、检票口、座位、酒店入住要求
- 联系电话、地址、地图入口
- 同行人和提醒

### 三级：查证与归档信息

- 订单号、预订平台、价格、附件、详细备注
- 创建时间、修改记录、来源信息

设计必须用层级降低认知负担，不能把所有字段平铺成卡片文本。

## 5. 空状态与异常状态

- 尚无旅行：解释产品价值并允许快速创建。
- 旅行尚无项目：以出行阶段给出添加建议。
- 时间冲突：展示影响与解决入口，不只显示红色错误。
- 同步失败：保留内容、说明状态、允许重试。
- 无网络：继续展示缓存，明确最后同步时间。
- 权限失效：说明哪些内容不可见以及如何请求访问。
- 项目取消：保留上下文，避免与正常项目视觉混淆。
- 跨时区：同时表达当地时间，必要时提供原时区参照。

## 6. 搜索语义

用户可能记得的不是标题，而是“MU5105”“虹桥”“银座酒店”“10 月 2 日”。搜索应覆盖结构化字段，并将结果放回旅行及日期上下文中。

## 7. 设计阶段可探索的方向

- 旅程作为连续空间、路径、章节、票夹或时间地形，而非普通待办列表。
- 当前时刻在旅程中的动态位置。
- 交通移动、停留住宿和自由活动采用不同空间语法。
- 将凭证视为可取用的“旅行物件”，而非附件链接。

这些是概念方向，不是指定界面。
