# 版本路线与验收标准

## 1. 里程碑

### M0：概念验证

- 完成产品需求与数据模型评审。
- 完成至少 3 个设计概念探索。
- 用一段真实但脱敏的复杂行程验证概念。
- 验证小程序登录、云端保存、订阅提醒等关键平台能力。

退出条件：选定一个能明显区别于备忘录、且可支撑 P0 场景的体验方向。

### M1：小程序内部 MVP

- 微信登录与账户。
- 旅行 CRUD。
- 7 类项目的手动录入与编辑。
- 旅行浏览、按日定位、当前与下一项。
- 搜索筛选、基础提醒。
- 本地缓存、同步状态与失败重试。
- 基础分享和角色权限。
- 个人页好友管理、旅行账单环形分类图与一键 AA 共享交互（原型阶段使用本机共享快照）。
- 好友账户号搜索添加与备注编辑；每项行程参与人选择及按项目分摊的 AA 明细。

退出条件：团队可用真实旅行连续使用，核心数据无丢失，关键流程通过验收。

### M2：小范围测试

- 酒店、航班、火车和城际巴士的结构化手动录入。
- 手动填写并展示项目间驾车衔接时长。
- 回收站与变更历史。
- 监控、错误报告、隐私协议与数据删除流程。
- 依据测试修正信息层级与录入成本。

退出条件：主要任务成功率达到预设门槛，严重隐私与同步问题清零。

### M3：Web 整理端

- 与微信账户绑定。
- 高信息密度浏览与编辑。
- 批量操作、附件管理、跨日调整。
- 与小程序同源同步与冲突处理。

## 2. P0 用户故事与验收

### 创建旅行

作为旅行规划者，我可以只输入必要信息创建旅行，再逐步完善。

验收：名称和日期足以创建；创建后立即可添加项目；刷新或换设备后仍存在。

### 添加交通

作为用户，我可以记录一段跨城市、可能跨时区的交通。

验收：起终点、当地时间和车次 / 航班号正确保存；跨日排序正确；详情可修改。尚未开票或尚未购买的火车 / 高铁可以设为“待抢票”，记录预计开售时间和期望席别，并设置开售提醒；出票后可在原项目上转为已确认。

### 添加住宿

作为用户，我可以把连续多晚住宿作为一个整体管理。

验收：入住与离店时间清晰；每天都能理解住宿关系；不会生成互相独立的重复住宿。

### 查看下一项

作为旅行中的用户，我打开产品即可知道下一步。

验收：进行中旅行优先；当前 / 下一项在不搜索、不切日期的情况下可找到；可直接导航或查看凭证。

### 处理变化

作为用户，我可以取消或修改项目而不丢失上下文。

验收：取消项目仍可查；相邻冲突重新计算；同行者看到最新状态。

### 多端同步

作为用户，我在一台设备编辑后，可在另一台设备继续。

验收：正常网络下变化最终一致；失败有可见状态；并发修改不静默覆盖。

### 分享旅行

作为所有者，我可以让同行者只查看或共同编辑。

验收：角色权限正确；邀请可撤销；敏感字段默认不可见；移除成员后无法继续获取新数据。

### 弱网查看

作为途中用户，我可以在无网时查看最近的关键信息。

验收：已缓存旅行可打开；显示最后同步时间；关键文本不依赖图片才能理解。

## 3. 发布前质量门槛

- P0 用户故事全部通过。
- 无已知的数据丢失、越权访问或敏感信息泄露问题。
- 主流程在常见手机尺寸和电脑版微信中可完成。
- 无网、慢网、重复提交和服务错误均有可恢复表现。
- 项目列表达到高数量时仍可使用。
- 字体放大、屏幕阅读器和减少动效得到基础验证。
- 隐私政策与实际采集、存储、分享行为一致。

## 4. 用于设计验证的示例旅行

建议用一段 6 天、3 城市的脱敏行程测试，至少包含：

- 跨日国际航班与时区变化
- 一段高铁和一段当地接驳
- 另一段尚未开票、带预计开售时间和提醒的“待抢票”高铁
- 两家酒店，其中一家连续住 3 晚
- 有准确时间与无准确时间的活动
- 一项取消安排和一组时间冲突
- 多张附件、一个只读同行者
- 离线状态和另一设备产生的修改冲突

简单的“单日三个事项”不足以证明设计可扩展。
